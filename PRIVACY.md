# Privacy and data flow

The browser attempts to remove selected identifiers and URL paths, queries, fragments and credentials. This is best-effort matching, not anonymization. Names, addresses, unusual identifiers, URL hosts and other sensitive content may remain. The user can edit and must confirm the preview before sending. A direct API caller can send raw input; the server also sanitizes it, but this does not prevent transmission to the server.

The application has no message database and does not deliberately log request text. A hosting provider or intermediary may retain technical data; review its actual configuration before deployment. If AI is requested, consented to and enabled by the operator, the server sends the remaining sanitized text to the configured OpenAI-compatible endpoint, including URL hosts. That endpoint may relay to another model provider. `store: false` is sent, but endpoint and upstream retention and processing depend on applicable terms and settings; this is not a zero-retention guarantee. No claim of GDPR compliance is made without an appropriate assessment.

If the operator enables commercial billing, Stripe processes payment and billing details under its own terms. The application stores a Stripe customer reference, order, subscription, invoice and webhook identifiers, amounts, status and an opaque workspace reference. It does not store card numbers. Account deletion removes the personal workspace and usage records after confirming there is no active subscription or pending checkout; minimal financial records and the Stripe customer mapping remain for later refunds and accounting. The workspace reference is derived from the former user ID, so this retention is **pseudonymous, not anonymous**. Operators must define lawful retention periods and handle access or erasure requests under their own obligations. Commercial billing remains disabled by default pending sandbox acceptance.

Optional PostHog EU analytics requires a separate browser choice; consent to AI does not enable analytics. When enabled by the operator and accepted by the visitor, the browser sends named page categories and limited business outcomes. Server telemetry for an opted-in visitor adds AI status, failure category, duration, token counts and estimated USD cost. Events use an app-scoped random ID, `app=overto_ai`, an environment label and schema version. Event projection strips message text, email, URL query/fragment, prompt and response content. Every event sets `$geoip_disable=true`; the shared PostHog project reported `anonymize_ips=true` on 2026-11-04. Network requests still expose the visitor's IP to PostHog during transport, so this is not an anonymity guarantee. Autocapture, session replay, feature flags and automatic exception capture are disabled. Browser/runtime errors are reported only as generic categories, without raw stack or message. Declining or withdrawing consent stops optional capture; the preference is stored in a first-party cookie. The hosting operator must recheck PostHog IP handling, retention and legal basis for its deployment. See [the observability guide](docs/observability/posthog.md).
