# Credit ledger and billing boundary

The self-hosted personal workspace uses PostgreSQL credit accounts. A request reserves credits under an idempotency key; settlement records consumption once or releases the reservation. Expired reservations are recovered when the account is accessed. The balance is calculated as **grants − consumption − active reservations − reversals**. The ledger serializes updates with an account row lock. A failed analysis does not consume a successful charge.

ROOT credit grants and their audit records share one transaction. Retries reuse a request ID, so a network timeout cannot silently issue the same grant twice. Refunds preserve the original grant and append compensating reversal rows. Signed Stripe Test Mode events are deduplicated, and refund accounting uses the original grant amount if configured allowances later change. An out-of-order refund is reconciled when the corresponding paid invoice is received.

The versioned plan catalog stores Free, monthly subscription and one-time credit pack definitions. Publishing a change adds a new version and audit record. Stripe Product and Price IDs are references; the catalog alone does not create a payment, charge a card or grant credits.

The new commercial billing path uses `billing_orders`, `billing_subscriptions`, `billing_invoices`, and `billing_webhook_events` in migration 022. Checkout reserves an order and checks the current catalog price against Stripe before redirecting. The dashboard shows real database records; a return URL never grants credits. The signed `/api/billing/webhook` handler checks Stripe mode, customer and order mappings, verifies a paid payment intent, and commits the event, invoice or order state, and credit grant in one PostgreSQL transaction. The same event or a duplicate paid event cannot grant twice. Refunds and disputes append credit reversals proportional to the original grant. Test and Live records are separated by mode.

**Rollout status (2026-11-07):** isolated QA passed a real Stripe Test Mode Checkout creation, signed webhook verification, a paid test subscription invoice and credit grant, full test refund and credit reversal, cancellation, and account deletion. The paid invoice was created through Stripe's test API using a test payment method; completion of the hosted Checkout form, renewal, payment failure, portal cancellation, and Live merchant/tax readiness remain unverified. `OVERTO_BILLING_MODE=disabled` and `OVERTO_BILLING_CHECKOUT_ENABLED=false` remain deployment defaults. Do not enable Live billing or advertise paid plans until the remaining sandbox flow and tax/legal configuration are verified.

To pause **new** payments after launch, leave `OVERTO_BILLING_MODE` and the Stripe webhook secret configured and set only `OVERTO_BILLING_CHECKOUT_ENABLED=false`. Existing subscriptions still need signed webhook processing and access to the customer portal for cancellation. Disabling the entire billing mode while subscriptions are active would prevent local reconciliation.

For a dedicated sandbox, configure the test secret and webhook signing secret privately, set `OVERTO_BILLING_MODE=test`, map current catalog versions to real Test Product and Price IDs, and set `OVERTO_BILLING_CHECKOUT_ENABLED=true` only for controlled QA. The webhook endpoint is `/api/billing/webhook`; subscribe to `checkout.session.completed`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `charge.refunded`, and `charge.dispute.created`. The flow currently permits card payments only. Set `OVERTO_STRIPE_AUTOMATIC_TAX=true` only after configuring Stripe Tax and reviewing the local tax obligations. Account deletion requires no active subscription or pending payment; expired linked Checkout sessions are verified with Stripe and, if still open, explicitly expired before deletion. Stripe verification failure blocks deletion. A minimal transaction reference and Stripe customer mapping remain for later refund reconciliation.

The legacy Stripe Test Mode subscription flow remains an isolated local experiment. The opt-in commercial QA test uses a Stripe test payment method and creates only sandbox transactions; it is skipped by default. With a dedicated `.env.ai-qa`, PostgreSQL volume, Mailpit, and Stripe CLI listener configured, run `OVERTO_STRIPE_QA_E2E=true npx playwright test e2e/commercial-stripe.qa.e2e.ts`. A Stripe Test Mode success is not proof of Live merchant, VAT, invoice or consumer-law readiness.

For PostgreSQL tests, use only a disposable local `overto_test` database through `LEDGER_TEST_DATABASE_URL` and `SITE_CONFIG_TEST_DATABASE_URL`. The test suite rejects other database names and non-loopback hosts. Do not point these variables at a production database.
