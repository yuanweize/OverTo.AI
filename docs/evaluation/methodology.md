# Evaluation methodology

The legacy 100-case dataset is a self-authored development set correlated with the rules. `challenge-dataset.ts` is a separate set of synthetic examples authored in this development session to cover family, banking, delivery, marketplace, investment, government, remote access, benign, ambiguous, URL and injection scenarios. It is **not independently annotated, blinded, real-world, representative, or protected from future tuning**. Labels and rationales are working hypotheses, not confirmed real-world incidents; an independent reviewer should audit them and build a held-out set before making effectiveness claims.

`npm run eval` runs the challenge set without making paid calls by default. Reports use an explicit truth-by-decision matrix. For the exploratory binary metrics, HIGH_RISK is positive and both other decisions are negative; ambiguous examples are excluded. VERIFICATION_RECOMMENDED and INSUFFICIENT_EVIDENCE are separately shown, so a non-high-risk outcome is never called safe. Under-warning counts malicious samples with insufficient evidence and also reports other non-high-risk malicious outcomes separately. Category counts are descriptive only, with small denominators.

A hybrid or model-only measurement is meaningful only when actual provider responses have been collected under a documented explicit opt-in, with a fixed model and protocol. Fallbacks cannot be counted as AI success. Mock calls are integration tests, not real model performance. Evidence hallucination and recommended-action safety require an explicit denominator and case-by-case inspection; without it they are **not measured**. Timing here is in-process wall time only, not HTTP, browser, or provider latency; spending is not inferred from it. Prior perfect-score reports are historical and misleading.

The tool does not verify sender identity or visit linked pages. Even a correct-looking classification is not evidence of real-world safety or verified benefit to users.
