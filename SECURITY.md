# Security

The API bounds request size and validates input. URL analysis parses locally and does not request the target. Configured OpenAI-compatible provider calls require explicit user consent, an operator-registered endpoint, a server-side key, a timeout and output limit. Coarse per-process rate and concurrency circuit breakers provide local resource protection, but are shared by all users, reset on restart, and do not coordinate across replicas. They are not a public abuse-prevention system. Authenticated local requests additionally use shared PostgreSQL limits per key, project and workspace, with fail-closed database admission. Project keys have scopes, expiration, rotation and a lineage-preserving daily request limit. Anonymous traffic still lacks shared identity-based controls. Production AI calls are blocked regardless of the legacy external-limits assertion; production API authentication and provider spending enforcement are not implemented. See [shared limit details](docs/administration/shared-limits.md). Do not expose the API publicly until those controls are implemented, configured and tested. No independent security audit has been completed.

Account functionality is explicitly development-only. Local email verification and password-reset messages are captured by Mailpit bound to loopback and are not delivered externally. Its inbox contains sensitive one-time links: never expose it publicly or use real accounts. Production email delivery, authentication deployment, distributed login limits and operational security are not implemented or validated. Password reset revokes existing sessions in local tests.

Do not put secrets in Git or client code. Redaction is incomplete; users should remove sensitive details before submission. Model output is untrusted and exact quotation matching does not ensure correct interpretation. For responsible disclosure contact the maintainer through a private channel; no public security contact has yet been configured.
